# Backoffice facts

Spec: `docs/features/backoffice/spec.md`. Start link: `docs/features/start-link/spec.md`. Decisions: `docs/adr/0031-the-backoffice-is-a-separate-host-signed-in-with-a-key-and-totp-enrolled-from-the-owners-terminal.md`, `docs/adr/0038-the-backoffice-signs-in-with-a-password-and-then-a-code-held-in-a-server-side-second-step.md` and `docs/adr/0032-whatsapp-numbers-are-rows-in-a-sealed-registry-not-worker-secrets.md`.

- **One Worker, two hosts.** `apps/api/src/backoffice/host-dispatch.ts` sends a request to the backoffice app only when its host and port equal `BACKOFFICE_ORIGIN`. The MCP host answers `404` to every backoffice path, and a host with a trailing dot answers `404` on every path. Neither app mounts the other's routes.
- **Two factors, one operator.** The password is hashed as `HMAC-SHA256(BACKOFFICE_PASSWORD_PEPPER, NFKC(password))` and then PBKDF2-SHA256 at 20000 iterations with a 16-byte salt, stored as `pbkdf2-sha256$<iterations>$<salt>$<hash>` with the lowercased email on the `backoffice_operator` row; the pepper is a Worker secret that never reaches D1, and the iteration count stays low because the Worker runs on the Free plan's 10 ms CPU. The TOTP secret is `BACKOFFICE_TOTP_SECRET`. Both secrets and the row are written only by `pnpm backoffice:enroll:<environment>` from the owner's terminal, because the script needs an interactive terminal. Never add a way to create, read back or reset them from the web.
- **Sign-in is two steps, flat and generic.** `POST /sign-in` takes an email and a password; a correct pair stores a pending row (digest of a random token, 5 minutes, one per operator) bound to the `__Host-zb_bo_pending` cookie. `POST /sign-in/code` deletes that row first, whatever the code, and only a right code against a live row opens a session. One failure answer for every cause. A per-address rate limit on both steps, then two D1 locks of 15 minutes after 10 consecutive failures each: a wrong password and an unknown email count on the password counter, which gates only `POST /sign-in`; a wrong code and a step-up key count on the code counter, which gates the code step, step-up and the password step. A missing, expired or used pending state counts nothing. An oversized or whitespace-only secret fails closed. The password hash always runs once (against a dummy hash for an unknown email) before the lock check. A TOTP step is accepted once.
- **Sessions.** The `__Host-` cookie holds a random token; D1 stores only its digest. 30 minutes idle, 8 hours absolute. The pending sign-in state is a separate table pruned with the sessions.
- **Step-up on every registry change.** Connecting, verifying, changing state and replacing a credential each need a fresh TOTP code, which shares the sign-in failure counter and lockout. A locked operator never has a code consumed. Connecting takes its code before Meta's popup and keeps it as one single-use grant of ten minutes in `backoffice_sessions.onboarding_grant_until`; the final post consumes it atomically before anything else happens ([ADR 0036](../../docs/adr/0036-one-fixed-meta-app-and-numbers-join-through-embedded-signup.md)).
- **Rejected forms redirect.** A failed sign-in is `303` to `/sign-in?notice=SignInFailed`; a rejected numbers form is `303` to its page with a single-use flash in `backoffice_sessions.flash` (one minute, same path only, non-secret values only, never a key, code, token or secret). The redirected GET answers the stored status: `401` code not accepted, `409` duplicate, `422` invalid.
- **CSRF.** A state-changing request needs an `Origin` equal to `BACKOFFICE_ORIGIN` and a valid HMAC form token; a missing `Origin` is refused.
- **No script, strict headers.** Pages are server-rendered Hono JSX with no client script, except `GET /numbers/connect/meta`, which loads the Facebook SDK and one `'self'` script under its own policy and `Cross-Origin-Opener-Policy: same-origin-allow-popups` ([ADR 0037](../../docs/adr/0037-only-the-onboarding-page-loads-the-facebook-sdk-under-its-own-policy.md)). The route marks its response with `PagePolicy.EmbeddedSignup`; every other response, errors included, carries the strict `Content-Security-Policy`, HSTS, `X-Frame-Options: DENY`, `no-store` and `noindex`; only the stylesheet and the script asset are cacheable.
- **Sealed credentials.** Access tokens are sealed with AES-256-GCM under `NUMBER_REGISTRY_KEY`, with the row and field as associated data, so a copied value fails to open. The one Meta app secret is the Worker secret `META_APP_SECRET`: it verifies every webhook (a missing one refuses every delivery) and authenticates the Embedded Signup code exchange. Plaintext exists only inside the Worker, for one request. Pages show "set, last changed" and never a value, a prefix or a length; the signup code, the PIN and the exchanged token reach no browser, log, error or flash. Only `apps/api/src/numbers/**`, `apps/api/src/backoffice/numbers/**`, `apps/api/src/adapters/d1/d1-number-registry.ts`, `apps/api/src/adapters/d1/d1-number-admin.ts` and the development seed name the `sealed_` columns; `tools/repository-shape/src/backoffice-isolation.test.ts` pins that.
- **Number states.** `pending` is ignored and refused; `pending` becomes `active` only when verified; `active` and `closed` switch both ways; `disabled` ignores inbound and refuses sends.
- **Templates are a checklist.** `verifyNumber` lists the templates of the number's WhatsApp Business account for every language, submits every missing one as Utility from `WHATSAPP_TEMPLATE_BODIES`, `WHATSAPP_TEMPLATE_QUICK_REPLIES` and `WHATSAPP_TEMPLATE_SAMPLES` (a refused submission stays missing, a rejected template is never resubmitted), and only for a matching number. The `template_recheck` job runs at minute 30 of every hour, repeats the check for each number whose stored snapshot has a template not Approved and records the snapshot only when the outcome is Verified, never moving `verifiedAt` ([ADR 0056](../../docs/adr/0056-templates-are-submitted-and-rechecked-automatically-for-every-number.md)).
- **Nothing identifying reaches an agent or a log.** No MCP result, connector frame, error message or log line carries a phone number ID, WABA ID, display number, token, app secret, key or client address. Logs carry event names and kinds only.
- **Audit.** Every action writes a `backoffice_audit` row with its outcome and the client address, kept 365 days and pruned by the daily scheduled job.
- **Isolation.** Nothing under `apps/api/src/mcp`, `apps/api/src/routes`, `apps/api/src/account-inbox`, `apps/connector` or `libs/` imports the backoffice or names a `backoffice_` table.
- **Metrics are read-only.** `GET /metrics` runs one `D1Database.batch` of `SELECT` statements; no other method is routed. Activity counts are written in the account's Durable Object (`activity_meter`, v8) and flushed hourly by `createActivityProvider` to `activity_daily` with the account's `number_id`; the page never adds a D1 write per message. Charts are inline SVG sized by attributes, so the strict Content-Security-Policy stays.
- **Language and theme are cookies.** `POST /locale` and `POST /theme` (behind the CSRF guard, never a `GET`) set `__Host-zb_bo_locale` and `__Host-zb_bo_theme` through `apps/api/src/backoffice/preference-cookie.ts`: `Secure`, `HttpOnly`, `SameSite=Lax`, `Path=/`, one year. Only allow-listed values are stored; `apps/api/src/backoffice/return-target.ts` allows only a backoffice page as the redirect, else `/`. The switches sit in the footer, drawn by `apps/api/src/web-shell` like the site's ([rule](web-shell.md)), and send the CSRF token with a `returnTo`. `Layout` writes `data-theme` from the `ShellTheme` member (`light`, `dark`, `system`), never from the cookie string. The icons are inline SVG with attributes and `currentColor`, sized by the `.icon` class, so the Content-Security-Policy does not change.
- **One stylesheet, tokens in three blocks.** `apps/api/src/backoffice/assets/backoffice.css` (served after `apps/api/src/web-shell/assets/shell.css`) names every colour only inside its three `:root` blocks (light; dark under `:root:not([data-theme='light'])` inside `prefers-color-scheme: dark`; the same dark palette under `:root[data-theme='dark']`, pinned equal by `tools/repository-shape/src/backoffice-tokens.test.ts`); every animation is switched off under `prefers-reduced-motion`, and a `forced-colors` block gives the hero card and the sparklines system colours. The contrast of the token pairs is proven from the file by `tools/repository-shape/src/backoffice-contrast.test.ts`.
- **The home is one batch of selects.** `apps/api/src/backoffice/home-sparklines.ts` reads the state counts and three 14-day series (numbers registered, messages, audit entries) in one `D1Database.batch` of `SELECT` statements, with `dailySeries` and `utcDay` from the metrics.
- **The start link follows the registry.** `GET /start` on the MCP host reads one display number per request, the oldest `active` one by `created_at` then `id`, with no cache, and answers `302` to a `wa.me` link built from a fixed origin, the validated digits and the fixed text of the `lang` locale; nothing else from the request reaches the target. No active number, or a stored number that fails the `+` and 7 to 15 digits pattern, answers the `503` page and never a redirect. It reuses `INSTALL_PAGE_LIMITER` under the `start:` key prefix. Closing a number sends new owners to the next active one on the next request (`docs/adr/0035-a-start-link-on-the-worker-picks-the-number-new-owners-write-to.md`).
- **Access opens in batches.** `GET /access` lists waitlisted accounts and email-waitlist entries without a live or used invite; `POST /access/release` and `POST /access/invite` take at most `ACCESS_BATCH_LIMIT` ticked rows (or the oldest matches of the filters when "select all" is ticked), a fresh step-up code and the CSRF token, and write one audit row whose target carries the counts. Release is the core use case `releaseAccountAccess` (one conditional `UPDATE ... WHERE state = 'waitlisted'`, repeat is a no-op) followed by `AccountOwnerRpc.noticeAccessOpened` in the account's Durable Object, which sends the message in the open window or queues it behind the notice template; a failed delivery is counted, never retried silently. Invite codes are `zbi_` plus 24 random characters, stored as a SHA-256 digest in `waitlist_invites`, shown once on the result page, redeemed by `redeemAccessInvite` from the first message of a waitlisted account in `apps/api/src/inbound/owner-inbound.ts` ([ADR 0043](../../docs/adr/0043-access-opens-in-batches-from-the-backoffice.md)). The metrics page reads the waitlist, invites, releases, messages and answered questions in its one batch of selects.
- **An operator's agent has a key and six tools.** `/agent-keys` (session, CSRF and a fresh step-up code to create; session and CSRF to revoke) mints `zbo_<16 hex>_<43 base64url>` keys shown once and stored as a SHA-256 digest in `backoffice_agent_keys`, with a label, a lifetime of 1 to 365 days (default 90) and a last-used stamp written at most once a minute. `POST /mcp` on the backoffice host takes `Authorization: Bearer <key>` only (no cookie, no CORS header, other methods `405`): the key id selects the row, the digest is compared in constant time, an unknown, wrong, revoked or expired key answers one `401` body, and `OPERATOR_KEY_RATE_LIMITER` (60 a minute, by key id) answers `429`. The tools are in `apps/api/src/backoffice/operator-mcp/operator-tools.ts`; `list_waitlist` lists only not-yet-invited entries (offset at most 1000) and writes a `waitlist.listed` row per call; `release_access` and `invite_waitlist` call `releaseBatch` and `issueInvites`, refuse without `confirm: true` or above `ACCESS_BATCH_LIMIT`, and write the Access page's audit row with `backoffice_audit.actor_key_id` (every `AuditEntry` carries `actorKeyId`, null for people; the Audit page shows the key). The route is mounted before `requestContext` and reads no session; a refused key counts against `ip:<address>` in the same limiter. No tool deletes an account, connects a number or touches a credential, and a key is never logged ([ADR 0046](../../docs/adr/0046-an-operator-agent-runs-the-backoffice-through-mcp-with-a-scoped-key.md)).
