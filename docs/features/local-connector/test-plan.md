## E2E (gate)

`apps/connector/test/e2e/connect.e2e.test.ts`, runs by default in the `e2e` gate (`pnpm --filter zapbip test:e2e`, which builds first). Starts `wrangler dev` (development entry, owner simulator) on an ephemeral port, runs `node dist/cli.js connect --client claude-code --cwd <temp dir>` with `ZAPBIP_CONNECTION_URL` pointing at the local stack, with the fake `claude` and `codex` on `PATH`. No real credentials, no third-party network.

Harness: `apps/connector/test/e2e/support/stack.ts` (fixed by the plan, file map L7).

- **Port.** The harness binds `net.createServer().listen(0, '127.0.0.1')`, reads the port, and closes the server. It passes that port as `wrangler dev --port <port>` and a second free port as `--inspector-port`. If wrangler exits with `EADDRINUSE`, the harness retries once with new ports; a second failure fails the suite with the port numbers in the message. No port is hard-coded.
- **Protocol.** `wrangler dev --local-protocol https`, so the connector's HTTPS-only validation (A10) runs unchanged. The child processes of the harness (the connector and the fake clients) get `NODE_TLS_REJECT_UNAUTHORIZED=0` in their environment only, never in `process.env` of the gate. Confirm at build that Node's global `WebSocket` honours it; if not, the harness sets `NODE_EXTRA_CA_CERTS` to the cert wrangler writes.
- **Secret.** The harness creates the connection through `apps/api/scripts/dev-seed.ts` (`--phone`, `--agents`, `--json`, `--persist-to`, run after `wrangler d1 migrations apply`, as `apps/api/test/e2e/global-setup.ts` does), which returns the connection secret and agent name. The harness reads nothing from `.env*`. The secret is passed to the connector only through `ZAPBIP_CONNECTION_URL` = `https://127.0.0.1:<port>/c/<secret>/mcp`, and to the fake client only through a file (below), never through argv.
- **Fake client MCP.** The fake `claude` reads the server list from the `--mcp-config=<file>` argument the connector passes (`{"mcpServers":{"zapbip":{"type":"http","url":"https://127.0.0.1:<port>/c/<secret>/mcp"}}}`), the file the connector itself writes with mode `600` and removes after the child exits. When `FAKE_CLIENT_CALLS_MCP=1`, the fake client performs the MCP calls: `POST` `initialize`, then the `notifications/initialized` notification, then `tools/call` with name `send_message`, `{agent, text}` where the text is `FAKE-REPLY ` followed by the owner text found inside the `<channel>` block of the wake prompt (the fake reads the prompt from standard input), the Streamable HTTP headers the SDK requires, and `Accept: application/json, text/event-stream`. `FAKE_CLIENT_USER_MCP_SERVERS` stands for the owner's own other MCP servers: without `--strict-mcp-config` the fake calls a `deploy` tool on each of them, so a second fake MCP server counts the requests it receives, and the test expects zero. The integration tests that do not set `FAKE_CLIENT_CALLS_MCP` never call MCP.
- **Assertion.** The owner simulator's screen (`readScreen`) must contain `FAKE-REPLY Oi` for the owner text `Oi`. The fake's own record (JSON lines) shows the `tools/call` response was `200`.

## Adversarial review

The reviewer picks the three claims most likely to be wrong and tries to refute each.

- [x] Claim 1: a message re-sent after a reconnect is never woken twice in one process run — attack: a `messages` frame arrives while the same message is queued and again after its wake finished before `done` was acknowledged; result: held — evidence: wake-queue unit cases "duplicate id while queued is ignored", "duplicate id while running is ignored" and "answers a message re-sent after its wake ended with done and no wake" (4dee916 unit.md); reconnect with a wake still running and done lost (6db08cc retest-unit-connector.md)
- [x] Claim 2: owner text cannot change the argv of a wake — attack: owner text starting with `--`, `-`, `resume`, a UUID, or containing `</channel>`; result: held at 6db08cc (hostile prompt on stdin, argv unchanged, tag escaped), re-run after the isolation change at cf219d3 — evidence: 237c8a3 final-head.md (hostile ids refused before spawn, owner text on stdin only); argv builders take no owner text; cf219d3 d-conn-unit.log 262/262
- [x] Claim 3: a replaced connector never reconnects and never runs a wake after the replacement — attack: replacement during an active wake, then a reconnect timer firing; result: open. Held for an idle replacement (6db08cc retest-unit-connector.md: exit 1, no reconnect); the attack with a wake running was not run — evidence: cf219d3 delta-head.md (bundle probe: connector 1 replaced mid-wake exits 1, no connector_reconnecting, no new run); committed connect.test.ts 'runs at most one wake per process and lets a replaced connector finish its running wake' and wake-queue.test.ts 'after stop the running wake finishes and no queued message starts'; committed in 6a4f8f4 (red); behaviour proven by committed tests + delta probes at cf219d3; red run not repeated, accepted (owner delegated 2026-11-06). Finding 2 of 237c8a3 final-head.md (the new connector re-runs the message still in flight) is outside this claim: replacement during an in-flight wake may run a message twice — accepted as at-least-once delivery, documented in spec + docs (owner delegated 2026-11-06)

## Coverage honesty

What is not tested and why.

- Real Codex behaviour (`enabled_tools`, the isolation flags and the sandbox on the pinned Codex CLI) — only the owner-run section and the spec's risk list cover them; the gate uses fake binaries. Real Claude Code was run once by hand through a shim (237c8a3 final-head.md), not in the gate.
- Cloudflare hibernation billing and the proxy's idle limit — documentation claims from ADR 0022, measured only in the owner-run section.
- Keychain or other secret storage — out of scope; the secret sits in a mode `600` file that the docs describe.
- The terminal prompt echo — a known limit (A8); no masking test beyond the link validation.
- Linux and Windows background services — documented, tested only on macOS in the owner-run section; Windows is not supported.
- Clients other than Claude Code and Codex, and wake replies other than `send_message` — out of scope by the spec.
- Codex app thread behaviour beyond the active-writer message — only the message string is tested, not the Codex app's own state.
- A connector whose reconnect is answered 401 after an accepted upgrade cannot read that status (Node's WebSocket hides it), so that path is NOT RUN. Row 129 is ticked on the refused-upgrade 401 probe, which is a different path.
- A replacement during an in-flight wake: the new connector runs the same message again while the replaced child still runs (237c8a3 final-head.md, Finding 2). No row covers it; the replaced connector itself never starts another wake (row 307).
- The wrangler development server's own access log prints the `/c/<secret>/` path (tool behaviour; the Worker's log lines carry no secret).
- A wake child still lists the names of the owner's user-level tools in its answer even with `--tools=` (6db08cc walk). Those tools are not callable (`dontAsk`), but the model still sees the list, so the docs' "cannot use other tools" holds only in effect.
