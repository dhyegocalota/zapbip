# Plan: Backoffice password sign-in

**Spec:** [spec.md](spec.md)
**Tier:** 🔴 structural
**Seam:** `apps/api/src/backoffice/auth/sign-in.ts` and `routes/sign-in-routes.tsx` are the only sign-in entry points; the step-up path (`auth/step-up.ts`) and the TOTP matcher (`auth/totp.ts`) are reused as they are.
**Assumptions (decided, owner can override):**
- One operator row, `backoffice_operator` (id 1). The password columns go on that row; no operators table.
- The lockout counter is the existing global one. Wrong passwords, unknown emails and wrong codes all count.
- Any submit to `/sign-in/code` consumes the pending state.
- The Worker stays on the Workers Free plan; the password hash is a pepper digest plus PBKDF2 at 20000 iterations (step 0, replaced).
- A wrong password or an unknown email counts toward the shared lock; any submit to `/sign-in/code` uses up the pending state.
- The tester walk uses a local-only operator created by the test support; its values live in the e2e fixtures and support files only.
- One developer lane. Every file below is owned by that one developer, in the order of the steps.

## Failure modes

| Step | What breaks | How I notice (the concrete signal) | How I back out |
|------|-------------|------------------------------------|----------------|
| 1 | The hash is over the Free plan's 10 ms CPU | The CPU-budget unit test fails; `wrangler tail` shows `Exceeded CPU` on `POST /sign-in` in staging | Lower `PASSWORD_HASH_ITERATIONS` through a new ADR; stored hashes carry their own count |
| 1 | `verifyPassword` accepts a case change or a stored string with a bad count | Unit test "refuses a case change" or "refuses a malformed string" goes green in the wrong direction | Revert the file; no data was written |
| 2 | Migration fails on a database with an existing `backoffice_operator` row | The integration test errors on `ALTER TABLE` with a duplicate column | Migration is additive: drop the new columns with a new migration if it was applied; the old Worker still runs |
| 3 | The sign-in page answers `503` on a configured Worker | The routes test "answers the sign-in page when configured" fails | Restore `BACKOFFICE_KEY_DIGEST` from `env.ts` and `require-configured.ts` |
| 4 | Pending rows leak (no prune) or a consume succeeds twice | The consume-twice test returns `true` on the second call | Revert `pending-sign-in.ts`; the table holds only expired rows, which the next sign-in clears |
| 5 | An unknown email skips the hash, so timing shows account existence | The spy test "verifies once for an unknown email" fails | Revert `sign-in.ts` to the step 4 state |
| 5 | A locked operator is refused before the hash | The spy test "verifies once while locked" fails | As above |
| 6 | A redirect or log carries the password or the email | The routes test asserting the `Location` value and the captured logs fails | Remove the offending field from the redirect; never log the form |
| 6 | The pending cookie lacks `__Host-` flags | The cookie test fails on `Secure` or `Path` | Fix the options in `backoffice-constants.ts`; the test is the proof |
| 7 | A switcher on `/sign-in/code` returns to the wrong page | The switcher test expects `/sign-in/code` and gets `/` | Add the path to `return-target.ts` (step 6) |
| 8 | The D1 statement writes the password instead of the hash | The unit test asserts the statement has no password substring | Revert `backoffice-enroll.ts`; the owner has not run it on production |
| 8 | The hidden prompt echoes the password | The output assertion in the enrollment test fails; in the owner's terminal, the echo shows | Restore the plain prompt only for the email |
| 9 | A rewritten test loses an assertion it used to make | The mutation check in `test-plan.md` (break lockout, see the security rows) stays green | Restore the assertion and add a case |
| 10 | A runbook step names a secret that does not exist | The runbook review and `rg` check find a live `BACKOFFICE_KEY_DIGEST` | Edit the runbook |

**Steps with no backout:** step 8 once the owner has run the new enrollment against a remote environment (the D1 reset overwrites `email` and `password_hash`, and the old key cannot be restored from the database; the owner re-runs the enrollment instead). Step 3 once `BACKOFFICE_KEY_DIGEST` is deleted in Cloudflare (the secret is gone; restoring it needs the old key, which nobody keeps).
