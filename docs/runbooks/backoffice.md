# Backoffice

Enroll the operator from your own terminal, sign in at the backoffice host, connect each WhatsApp number through Meta's onboarding, verify and activate it, replace its access token and recover from a lockout.

You do all of this by hand ([ADR 0031](../adr/0031-the-backoffice-is-a-separate-host-signed-in-with-a-key-and-totp-enrolled-from-the-owners-terminal.md), [ADR 0032](../adr/0032-whatsapp-numbers-are-rows-in-a-sealed-registry-not-worker-secrets.md)). Enrollment needs your terminal and your Cloudflare token, and the registry forms need your key, your authenticator, your Facebook sign-in and each number's PIN, so an agent never runs `pnpm backoffice:enroll:development`, `pnpm backoffice:enroll:staging` or `pnpm backoffice:enroll:production` (the deploy guard refuses them), never signs in and never sees a key, a code, a PIN, an app secret or an access token. An agent may read this runbook and run the read-only host checks of [dns.md](dns.md), step 3. The staging host is `https://backoffice-staging.zapbip.com` and the production host is `https://backoffice.zapbip.com`. The migrations of [deploy.md](deploy.md), step 4, come first.

1. **Enroll the operator.** In your own interactive terminal, with `CLOUDFLARE_API_TOKEN` exported as in [deploy.md](deploy.md), run `pnpm backoffice:enroll:staging` (for production `pnpm backoffice:enroll:production`, which also asks you to type `production`). The script prints the backoffice key once, beginning `zb_bo_`, and a QR code. Scan the QR code with your authenticator app (or type the printed text secret), then type the current six-digit code. Store the key in your password manager, then press Enter: the screen and the scrollback are cleared.

   Expect: `pnpm --filter @zapbip/api exec wrangler secret list --env staging` (production: no `--env`) names `BACKOFFICE_KEY_DIGEST` and `BACKOFFICE_TOTP_SECRET`. The key never appears on a command line, in a file or in the log.

   If it fails: a refusal that mentions a terminal means stdin or stdout is not interactive; run it in your own terminal tab. A code mismatch stops the script before anything is written; run it again. A D1 error naming `backoffice_operator` means migration `0005` is not applied; run the migrate step first. Use a separate enrollment for each environment: the staging key does not sign in to production.

2. **Sign in and connect the number.** Open the backoffice host, type the key and the current authenticator code, and choose Sign in. Before you connect a second number, run `pnpm --filter @zapbip/api exec wrangler d1 execute zapbip-production --remote --command "SELECT COUNT(*) FROM accounts WHERE number_id IS NULL"` from your own terminal (on staging run `wrangler d1 execute zapbip-staging --env staging --remote` instead of `zapbip-production --remote`): the first number binds those accounts only while it is the only one, and an account left without a number when a second number exists is dropped. Open Numbers, Connect a WhatsApp number, type a fresh authenticator code and choose Continue: the code opens the connect page for 10 minutes and one attempt. Type a label and the number's six-digit PIN ([meta-setup.md](meta-setup.md), step 5), then choose Connect. In the Meta popup sign in with the Facebook account that administers the Business portfolio, pick the portfolio, create or pick the WhatsApp Business account, add or pick the number, enter the code Meta sends to it and set the display name. When the popup closes, the backoffice finishes on its own: it subscribes the app to that account, registers the number with the PIN, reads the display number and stores the number. Then add the payment method ([meta-setup.md](meta-setup.md), step 9).

   Expect: the number is listed as Pending with the display number Meta reported, and "Number registered. Verify it before activating." shows. No page shows the token, the code or the PIN. The first number connected also binds any account that has none. Before a second number, the count command prints `0`.

   If it fails: "Code not accepted" means the step-up code was already used or expired; wait for the next code. A failure naming `exchange`, `inspect`, `read`, `subscribe`, `register` or `override` stored nothing (`webhook_claimed_elsewhere` means the number already delivers to another environment, so no change was made at Meta; `not_granted` means the WABA was not among the assets chosen in the popup): start again from Connect a WhatsApp number, because the Meta code lives 30 seconds and each attempt needs a new one. `register` with `auth` or `upstream` is usually a PIN that differs from the number's two-step PIN. A popup that says the domain is not allowed means [meta-setup.md](meta-setup.md), step 3, is missing this host. Closing the popup only shows a cancelled line; try again while the 10 minutes last. "Already registered" means that phone number ID is in the registry already. If the count is not `0`, connect no second number: finish the first number's binding or fix the unbound accounts first. The key and code failing ten times in a row lock the operator for 15 minutes (step 6).

3. **Verify the number with Meta.** Open the number, choose Verify with Meta and type a fresh code. The backoffice asks Meta for the number's display number and the status of the templates `zapbip_agent_notice` and `zapbip_agent_question` in `pt_BR` and `en_US`.

   Expect: "Number verified." and the four template statuses; the display number matches the one you registered. Templates that are not yet approved only warn that notices outside the 24-hour window will fail.

   If it fails: the page names the kind of failure. `auth` means the access token was revoked or lacks `whatsapp_business_messaging`; replace it (step 5). `not_found` means the phone number ID or the WABA ID is wrong. `network` or `upstream` means Meta did not answer; retry in a minute.

4. **Activate the number.** Activate only after step 8 of [meta-setup.md](meta-setup.md) shows the webhook verified for that number's environment: an Active number without a verified webhook receives new owners from the start link but never hears them. On the number page choose Change state, Active, and type a fresh code. Use Closed to stop accepting new accounts while keeping the existing ones: the start link (`https://mcp.zapbip.com/start`) sends new owners to the oldest Active number, so closing a full number moves them to the next Active one on the next click, and with none Active it shows the "back soon" page. Use Disabled only to stop the number completely.

   Expect: the number shows Active in the list. With the webhook of the environment verified ([meta-setup.md](meta-setup.md), step 8), a message from your phone to this number reaches your agents and replies are sent from it.

   If it fails: "Verify the number first" means step 3 has not succeeded; a Pending number cannot become Active.

5. **Replace a credential.** For a new access token, generate one in Business settings, System users, for the number's WhatsApp Business account with `whatsapp_business_messaging` and `whatsapp_business_management`, then open the number, Replace access token, paste it and type a fresh code. The app secret is not in the backoffice: after a Reset in Meta ([meta-setup.md](meta-setup.md), step 6) set `META_APP_SECRET` again in both environments ([deploy.md](deploy.md), step 3). `NUMBER_REGISTRY_KEY` itself is not rotated: a new key cannot open the stored tokens, so you would connect every number again.

   Expect: "Access token replaced.", and the next send uses the new token without a deploy; after a new `META_APP_SECRET`, the next webhook is accepted.

   If it fails: a rejected code is the step-up message of step 2. A webhook that Meta rejects with `401` after a secret reset means an environment still holds the old `META_APP_SECRET`.

6. **Recover: re-enroll or wait out a lockout.** A lost authenticator, a lost key, a suspected leak and a lockout (ten consecutive failures lock sign-in for 15 minutes, even with the right factors) are all fixed the same way: run step 1 again. It issues a new key and a new authenticator entry, invalidates the old ones, drops every session and clears the lock. There are no recovery codes. After a lockout you may instead wait 15 minutes.

   Expect: the old key and the old authenticator entry are refused, the new pair signs in, and the audit log shows `operator.enrolled`.

   If it fails: if the enrollment script cannot write the secrets, the Cloudflare token is missing a permission ([cloudflare-setup.md](cloudflare-setup.md), step 4). Remove the old authenticator entry yourself.
